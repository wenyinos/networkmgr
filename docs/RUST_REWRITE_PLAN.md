# NetworkMgr 用 Rust 重写的完整方案（egui / eframe）

- 方案基准：仓库 `670dd45`（NetworkMgr 7.0）
- 编写日期：2026-11-07
- 目标：**保持原项目全部功能与外部契约**，图形层改用 egui / eframe
- 本文件只做设计，不含代码改动

---

## 0. 结论先行

**可行，但不能"把 GTK 换成 egui"这么理解。** egui / eframe 是即时模式的**窗口**框架，不提供系统托盘；而 NetworkMgr 的核心形态就是一个常驻托盘图标。因此架构上必须拆成两件事：

| 部件 | 用什么 | 理由 |
|---|---|---|
| 系统托盘 + 右键菜单 | `tray-icon` + `muda` 原生菜单 | egui 无法绘制原生托盘菜单；强行用 egui 弹窗模拟会丢失观感与桌面集成 |
| 配置窗口、密码/EAP 对话框 | **egui / eframe**（满足本次技术选型） | 这是用户可见的窗口部分，也是 egui 的适用场景 |

**推荐路径是渐进式四阶段，而不是一次性全量重写。** 理由：当前 49 条界面字符串背后，是 `wpa_cli` 控制协议、SSID printf 转义、`rc.conf` 注入防护、devd 事件链和 FreeBSD port 打包这一整条链路；一次性切换后任何回归都无法定位。每阶段保留可回退的旧二进制。

**最大风险是 P0 级的三个**：sudo 下运行 GUI 与 D-Bus 的冲突、eframe 没有"无窗口常驻"的标准用法、以及**验收环境的先天缺口**（VM 无 3D 加速、无真实无线网卡、无 sudo、GitHub 直连超时）。原先把"无法验证 FreeBSD 构建"列为 P0，现已因本机存在 FreeBSD 15 VM 而解除，改为在 guest 内原生构建；随之暴露的新缺口见第 13、14 节。

## 1. 兼容性具体指什么：必须冻结的外部契约

"尽量保持兼容"要落到可逐项验收的清单上，而不是感觉。以下是当前仓库对系统/用户作出的承诺：

### 1.1 路径与入口（不可变）

| 契约 | 当前值 | 来源 |
|---|---|---|
| 托盘可执行文件 | `/usr/local/bin/networkmgr` | `setup.py` scripts、desktop、`sudoers` |
| 配置窗口可执行文件 | `/usr/local/bin/networkmgr_configuration` | `setup.py` scripts |
| 自启动 | `$PREFIX/etc/xdg/autostart/networkmgr.desktop`，`Exec=sudo networkmgr` | `src/networkmgr.desktop` |
| 提权 | `%operator ALL=(ALL) NOPASSWD: /usr/local/bin/networkmgr` | `src/sudoers.d/networkmgr` |
| devd 规则 | `/usr/local/etc/devd/networkmgr.conf` | `src/networkmgr.conf` |
| devd 动作脚本 | `/usr/local/share/networkmgr/{setup-nic,link-up,auto-switch}.py` | 同上 |
| wpa 模板 | `/usr/local/share/networkmgr/wpa_supplicant.conf` | `setup.py` |
| 图标 | `$PREFIX/share/icons/hicolor/**`（183 PNG + 13 SVG） | `src/icons/` |
| 翻译 | `/usr/local/share/locale/*/LC_MESSAGES/NetworkMgr.mo`（7 语言） | `po/`、gettext domain `NetworkMgr` |

### 1.2 系统状态与命令（读写格式不可变）

- `rc.conf` / `rc.conf.local` —— 一律经 `sysrc` 读写，变量名如 `ifconfig_em0_10`
- `/etc/resolv.conf` —— 由程序重写，首行 `# Generated by NetworkMgr`
- `/etc/wpa_supplicant.conf` —— 权限 `0600 root:wheel`，含明文密码
- `$PREFIX/etc/wireguard/*.conf` —— 用 `# Name = ` 注释承载显示名
- 命令：`ifconfig`、`sysrc`、`service`（netif / dhclient / routing）、`netstat -rn`、`wpa_cli -p /var/run/wpa_supplicant`、`wg`、`wg-quick`、`/etc/pccard_ether`

### 1.3 用户可见功能（逐项等价）

1. 托盘菜单：WireGuard 区、有线区、WiFi 区、`Restart Networking`、`Close Network Manager`
2. 托盘状态：按信号强度选图标、连接中 300 ms 帧动画、tooltip、30 秒被动刷新、菜单打开时才采集完整数据
3. 有线：启用/禁用；DHCP 或静态 IPv4 与 IPv6（地址、掩码/前缀、网关、DNS、搜索域）；SLAAC
4. 无线：扫描、`WPA3 only` 标记、开放网络 / WPA-PSK / 企业级 802.1X 连接、断开、忘记网络
5. 连接策略：**连接成功才保存 network block**；失败累计 3 次（`MAX_ATTEMPTS`）才删除；超时与 daemon 拒绝分两种文案
6. EAP 对话框：PEAP / TTLS / TLS / LEAP / FAST / PWD + Phase2，CA 证书、客户端证书、私钥文件选择，密码显隐，匿名身份
7. WireGuard：`wg-quick up/down`、`wg show` 判活、`sysrc -n wireguard_enable` 判服务
8. devd：网卡 ATTACH 自动声明、LINK_DOWN 切换默认路由、LINK_UP 恢复 DHCP
9. 多语言：7 个 `.po`，运行时按 locale 读 `.mo`

### 1.4 需要澄清（不是契约，是现存疑点）

- README 声称支持 `openrc(8)`，但全仓库除 README 外**没有任何 openrc 分支**，后端命令全是 FreeBSD `rc(8)` 的 `service` / `sysrc` / `netif`。重写前必须确认这是文档措辞还是确有部署场景。
- README 要求用户加入 `wheel` 组，`sudoers.d` 却授权 `%operator`。两者不能都当契约，需定一个。
- `setup.py:22` 与 `wg_api.py:14` 都是 `'/usr/local' if system() == 'FreeBSD' else sys.prefix`。DragonFlyBSD 会落到 `sys.prefix`，与"支持 DragonFlyBSD"的声明存在偏差；Rust 版应显式按 OS 列表判定，别照抄这个 bug。

**平台支持（关键结论）：**

- 它有两个后端：默认 `libappindicator`（GTK3 + libappindicator / libayatana-appindicator，同时启用 `muda-gtk3`），以及 `ksni`（StatusNotifierItem D-Bus，**不依赖 GTK**，自带 worker 线程）。两者同开会优先用 ksni 并告警。
- README 给出的 FreeBSD 编译依赖：`pkg install -y rust glib pkgconf gtk3`。`libappindicator` 在 FreeBSD 上是否需单独装，实机确认。
- `winit` 的 Unix 后端 cfg 明确包含 `freebsd` / `dragonfly` / `netbsd` / `openbsd`，历史 changelog 有 "On FreeBSD, NetBSD, and OpenBSD, fix build of X11 backend" 记录。

- eframe 0.37 的 `system_fonts` feature 走 `egui_system_font_provider`；**egui 默认字体不含 CJK**，中文界面必须靠它或自带字体，否则全部显示豆腐块。

## 3. 架构设计

### 3.1 进程模型（推荐：双二进制，对应现有两个入口）

```
networkmgr                       ← 常驻托盘进程（tray-icon + winit 事件循环）
  ├─ 原生托盘菜单 (muda/AppIndicator)
  ├─ 后台刷新线程 ── mpsc ──> 菜单状态快照 (ArcSwap)
  └─ 点击 "Configure %s" ─exec─> networkmgr_configuration

networkmgr_configuration [nic]   ← 独立窗口进程（eframe::run_native）
  ├─ IPv4 / IPv6 配置窗口
  ├─ PSK 密码对话框
  └─ EAP 凭据对话框

networkmgr-devd <subcommand>     ← 阶段 4 才引入，替换三个 Python 脚本
```

**为什么拆进程**：原仓库本来就是两个入口脚本，desktop 与 sudoers 都只认 `networkmgr`；拆进程后这两个文件一行都不用改。同时规避了"eframe 常驻但无可见窗口"这个没有标准解法的问题——配置窗口进程天然是显式打开、关闭即退出。

**备选（单进程）**：用 eframe 的自定义事件循环入口（0.32 起文档列有 `create_native`，0.37 的 API 需实现前复核）配合 `TrayIconEvent::set_event_handler` + `EventLoopProxy` 转发托盘事件，主窗口初始隐藏。可行但耦合更紧、回退更难，不作为首选。

### 3.2 代码组织（单 crate 多 bin，不为将来扩展预留抽象）

```
Cargo.toml            # 一个 package，3 个 [[bin]]
src/
  bin/networkmgr.rs                 # 托盘入口
  bin/networkmgr_configuration.rs   # 窗口入口
  bin/networkmgr-devd.rs            # 阶段 4，可选
  sys.rs        # Command 统一封装：列表参数、capture、超时、错误反馈
  model.rs      # Nic / WifiNetwork / WgTunnel / TrayState 等纯数据类型
  wifi.rs       # ifconfig 解析、信号强度、状态机
  wpa.rs        # wpa_cli 协议、printf 编解码、network block 读写
  config.rs     # rc.conf / resolv.conf / wpa_supplicant.conf 读写
  validate.rs   # validate.py 的逐条移植
  wg.rs         # WireGuard
  i18n.rs       # .mo 加载 + tr!()
  ui/           # egui 的窗口与对话框
    mod.rs  config_window.rs  passphrase.rs  eap.rs
```

`sys.rs` 是唯一允许 `std::process::Command` 的地方，所有其它模块只依赖 trait/函数签名——**这不是为了"架构优雅"，而是让第 6 节的契约测试能在 Fedora 上用假输出跑起来**。

### 3.3 线程与事件模型（对应原 GTK 模型）

| 原实现 | Rust 等价 |
|---|---|
| GTK 主线程 | eframe / winit 主线程 |
| `update_tray_loop()` daemon 线程，30 秒一轮 | `std::thread::spawn` + 30 秒循环 |
| `GLib.idle_add(self.update_tray)` | `mpsc::Sender<State>` → UI 线程 `try_recv` + `ctx.request_repaint()` |
| `_thread.start_new_thread` 发起连接 | 同一后台线程池，结果同样走 channel 回传 |
| `tray_state()` 先建完整 dict 再赋值，无锁 | 一次构造完整 `TrayState` 快照再整体替换（短临界区 `Mutex`，或用 `arc-swap`），读侧永远看到完整快照、不会看到半构造状态 |
| `GLib.timeout_add(300, ...)` 图标动画 | 每帧 `request_repaint_after(300ms)` |
| `Gtk.Menu` 回调 | `MenuEvent::set_event_handler` → `EventLoopProxy` → 主循环分发 |

硬规矩：**后台线程绝不触碰任何 UI 状态**；所有子进程调用都要有明确错误反馈，禁止静默 `let _ =`。

## 5. 两个必须专门决策的点

### 5.1 托盘后端：`libappindicator` 还是 `ksni`

| | libappindicator（默认） | ksni |
|---|---|---|
| GTK 依赖 | 有（gtk3 + appindicator） | 无 |
| 桌面兼容 | 与现有 GTK3 托盘行为最接近，MATE/XFCE 友好；**Cinnamon 实测可用**（无 watcher 时自动回退 XEmbed） | 需桌面实现 StatusNotifierItem；**Cinnamon 不提供 watcher，实测不可用** |
| 事件循环 | **要求调用线程上有事件循环在跑** | 自带 worker 线程 |
| sudo 运行 | 走 X11，与原 Python 版一致 | 需要 session D-Bus，`sudo` 下通常拿不到 → **高风险** |

**推荐默认 `libappindicator`**：因为现有 `Exec=sudo networkmgr` 是硬契约，而 sudo 环境不保证 session bus。若将来把提权模型改成"普通用户跑 GUI + 特权操作单独提权"，再切 `ksni` 以彻底去掉 GTK。这个取舍要在第 12 节向维护者确认。

**2026-11-09 Cinnamon 实测补充（见第 41 节）**：Cinnamon 6.4.13 不提供
`org.kde.StatusNotifierWatcher`，但 `libayatana-appindicator` 会自动回退到 legacy **XEmbed**
嵌入，Cinnamon 的 systray 依然接受，图标 24×24 正常显示。这条推翻了"桌面必须实现
StatusNotifierItem 才能用"的默认假设，也说明 §41 里把探测目标从 watcher 改成 bus 本身是必要的。

### 5.2 翻译：不要引入新的系统依赖

Python 的 `gettext` 是**纯 Python 解析 `.mo`**，不链接系统 `libintl`。`gettext-rs` 属于 `libintl` 的 FFI 绑定方案，会引入 C 侧构建/运行依赖（具体是否链接系统 gettext 取决于 feature，需在 FreeBSD 实机核实），对本项目属于无谓的兼容性倒退。

**推荐**：在 `i18n.rs` 里写一个约百行的 `.mo` 读取器（GNU MO 格式固定：magic、偏移表、原串/译串表），按 `LANG` 找 `/usr/local/share/locale/<lang>/LC_MESSAGES/NetworkMgr.mo`，复数规则沿用现有 `.po` 头。这样 `po/` 与 `.mo` 安装布局完全不变，7 个语言无需重新翻译。

另需调整提取链：`xgettext -L Python` 不认识 `.rs`。保留现有 `po/networkmgr.pot` 作为基准，用 `xtr` 或一段小脚本从 `tr!()` 宏提取并 `msgmerge`；`po/POTFILES.in` 目前只列了没有任何字符串的 `networkmgr_configuration`，本就要修。

### 5.3 图标与字体

- 图标复用 `src/icons/` 的 PNG，用 `image` 0.25.10 解码成 RGBA 交给 `tray_icon::Icon::from_rgba` / `egui::ColorImage`；`signal_icon_name()` 的命名规则照搬，不重新设计资源。
- 中文（以及俄文等）需要 CJK 字形：开启 eframe `system_fonts`，或在 `CreationContext` 里用 `egui::FontDefinitions` 加载系统字体。**这是 P1，不处理会让刚补完的简中翻译全部显示为方块。**

## 6. 分阶段实施（每阶段可独立验证与回退）

**阶段 0 — 契约冻结（P0）**
- **先做两个 spike，不过关就不写业务代码**（见第 14 节）：① 最小 eframe/glow 窗口在 `vmvga` 软件渲染下能否起来；② 最小 tray-icon 图标能否出现在 Xfce 面板。
- 在 `freebsd15` VM 内 `pkg install rust` 原生构建，配好 crate 获取通路（镜像或 vendor）。
- 采集真实样本：`ifconfig`、`wpa_cli status/list_networks/scan_results`、`netstat -rn`、`sysrc -n`，特别是含引号与中文的 SSID。VM 无真实无线网卡，wpa 样本从 `X200-BSD` 实体机或一次性录制获取。
- 在 `sys.rs` 之上写契约测试：喂样本 → 断言解析结果。这类测试**在 Fedora 上就能跑**。
- 把 `validate.py` 的行为整理成对照表，逐条在 Rust 侧写等价测试（含全部拒绝用例）。
- 验收：两个 spike 通过；契约测试全绿；样本入库 `tests/fixtures/`。

## 7. 安全与正确性红线（P0，不可"顺手优化"）

1. **`rc.conf` 是开机时以 root 执行的 shell 脚本，而 `sysrc` 写值只套双引号、不做转义。** Rust 的 `Command` 参数列表只防住了"命令拼接注入"，防不住写入值本身变成 shell 代码。`validate.py` 的每一条规则必须原样移植，任何绕过校验的写路径都视为缺陷。
2. **SSID 的 printf 编解码必须逐字节复刻。** 原实现里曾有"直接跟普通字符串比较会静默不匹配"的坑；含 `"`、`\`、中文的 SSID 是必测用例。
3. `wpa_supplicant.conf` 保持 `0600 root:wheel`；私钥路径与密码不写日志、不进错误信息。
4. `MAX_ATTEMPTS = 3`、连接成功才保存、失败文案区分"超时"与"daemon 拒绝"——这些是 issue #81 修出来的行为，别当成可以简化的历史包袱。
5. `rc_conf_interface()` 的 `.-/+` → `_` 映射（对应 `rc.subr` 的 `get_if_var`）保留。
6. 不改动认证/加密流程，不新增"为将来扩展"的抽象层。

## 15. 本轮补充的设计缺口

### 15.1 统一的超时与错误策略（原来散落在各处）

Rust 侧把下列常量集中在 `sys.rs`，禁止各处硬编码；每个子进程调用都必须返回带上下文的 `Result`，禁止静默吞错：

| 场景 | 现值（来自 Python 源码） | Rust 处理 |
|---|---|---|
| `wpa_cli` 单次调用 | 5 秒超时 | `Command` + 超时包装，`FAIL`/非零/无 daemon → 明确的 `WpaUnavailable` |
| `wait_for_connection` | 30 秒 | 后台任务内轮询，可取消 |
| `wait_for_address` | 5 秒 | 同上 |
| `wait_for_daemon` | 5 秒 | 同上 |
| 托盘被动刷新 | 30 秒一轮 | 定时器线程，失败记日志并保留上一份快照 |
| 连接动画 | 300 ms / 帧 | `request_repaint_after` |
| 连接重试 | `MAX_ATTEMPTS = 3` | 常量，见 15.2 |
| 写入校验 | 搜索域 ≤6 个且 ≤256 字符等 | `validate.rs`，全部拒绝用例写测试 |

### 15.2 连接状态机与取消（原方案没定义）

原 Python 版用 `self.connecting` 布尔 + 后台线程 + `idle_add`，没有处理"连接中用户切到另一个网络或点退出"。Rust 侧定：

- **只有一个连接任务在跑**，`ConnectionState`（Idle / Connecting{ssid,card,attempt} / Failed / Connected）由后台任务持有，UI 只发命令、只读快照。
- 取消用显式 token（`AtomicBool` 或 channel 丢弃），发新连接前先取消旧任务；窗口关闭/进程退出时 join 并置 Idle。
- 3 次重试在后台任务内循环，每轮检查取消；"连接成功才保存 network block"仍由后台任务执行。
- UI 在任何失败态都要给出可见反馈（对应 Python 的 `connection_failed` / `reopen_credentials_dialog`），不得静默。

### 15.3 契约测试的具体形态（原方案只说"输出 JSON 比对"）

- Python 版**不改源码**：新增一次性脚本 `tools/dump_state.py`，`from NetworkMgr.net_api import tray_state` 后 `json.dumps(..., sort_keys=True, ensure_ascii=False)` 输出。
- Rust 侧加隐藏开关 `--dump-state`，输出**同一 schema**；两侧在同一台 C 类机器上、同一网络状态下逐字段 `diff`。
- 命令输出样本（`ifconfig` / `wpa_cli` / `netstat` / `sysrc`）存 `tests/fixtures/`；Rust 的 `sys.rs` 之上用 trait 注入假输出，让 A 类环境也能跑全部解析测试。
- 含 `"`、`\`、中文的 SSID 必须各有一份样本与往返测试。

### 15.4 翻译提取链定案（原方案在 `xtr` 与脚本间摇摆）

**采用自写脚本，不引入新依赖**：`tools/extract-i18n.py`（约 30 行）扫 Rust 源里的 `tr!("...")`，生成 gettext 可读的临时 POT 片段，再 `msgmerge -U` 合并进现有 `po/*.po`。保留 `po/networkmgr.pot` 作为基线、保留 7 个语言的既有译文；修正 `po/POTFILES.in` 使其列出真正的 Rust 源文件。理由：符合"简单优先、不引新依赖"，且 `xtr` 在 BSD 上的可用性还需额外验证。

### 15.5 日志与可观测性（原方案完全缺失）

- 日志落 `$XDG_DATA_HOME/networkmgr/networkmgr.log`，同时把启动失败/托盘创建失败写到 stderr（自启动失败时桌面不会显示任何东西）。
- 每条记录：命令名、脱敏后的参数、返回码、耗时；**SSID 可记，密码、私钥路径、EAP 身份一律不记**。
- 提供 `-v` 开 debug；UI 上每个失败动作都要有可见错误提示（对应用户约定的"异步 I/O 必须有错误反馈，严禁静默失败"）。
- "托盘图标没出现"的排查顺序写进文档：日志 → spike ② → 面板插件 → D-Bus session → X11 授权。

### 15.6 并行安装与回滚（原方案只写了一句"留 .py"）

因为 `rc.conf` / `resolv.conf` / `wpa_supplicant.conf` 格式完全不变，**新旧两版可以交替启动**，这是回滚成立的前提：

### 15.8 决策记录（ADR）与重审条件

| 决策 | 理由 | 什么情况下重审 |
|---|---|---|
| 托盘用原生 `muda`，窗口用 egui | egui 无系统托盘 | egui 生态出现官方托盘支持 |
| `libappindicator` 而非 `ksni` | `Exec=sudo networkmgr` 是硬契约，sudo 下 session D-Bus 不可靠 | 提权模型改为普通用户运行 + 特权操作单独提权 |
| 双二进制而非单进程 | eframe 无"无窗口常驻"标准用法 | eframe 提供稳定的 headless 事件循环接口 |
| 纯 Rust `.mo` 解析而非 `gettext-rs` | 避免引入 libintl，保持零新增系统依赖 | 需要复数形式、`pgettext` 上下文等高级特性 |
| `glow + x11`，关 `wgpu/wayland` | 依赖更少、体积更小、X11 路径成熟 | spike ① 失败，或目标平台转向 Wayland |
| 四阶段渐进 | 每阶段可回退、可定位回归 | 上游要求一次性替换 |
| guest 内原生构建 | 宿主无 freebsd target / cross / zig | 引入 `cross` 或远端 FreeBSD CI runner |

## 41. 实机缺陷修复（2026-11-09，来自 Cinnamon 桌面测试报告）

用户在 FreeBSD 15.1 + Cinnamon 6.4.13 上实测 0.1.0 的 pkg，提交了四个缺陷，逐条修复。

### P0｜干净系统上托盘 panic（退出码 101）

- **现象**：装完 pkg 启动无窗口、无图标、无提示，约 30 秒后进程消失，退出码 101。
- **根因**：`libayatana-appindicator` 是 tray-icon 用 **dlopen** 加载的，不在 ELF 的 `NEEDED`
  里，所以 `pkg create` 的依赖扫描发现不了；`+MANIFEST` 又没手写 `deps`。
- **修复**：
  1. `build-pkg.sh` 的 `+MANIFEST` 增加
     `deps: { gtk3: {origin: "x11-toolkits/gtk30"}, "libayatana-appindicator": {origin: "x11-toolkits/libayatana-appindicator"} }`；
  2. 代码侧在 `gtk::init()` 前加 `ensure_tray_library()`，检查四个候选 `.so` 路径，缺失时打印
     中英双语提示（含 `pkg install` 命令）并 `exit(1)`，不再吐 Rust backtrace。

### P1｜启动固定延迟 30–75 秒

- **两个根因**：① `find_status_notifier_bus()` 只扫 `/tmp/dbus-*`，且探测目标写成
  `org.kde.StatusNotifierWatcher`——Cinnamon 不提供该服务，于是活着的 bus 也全被判 false；
  ② `dbus-send` 默认回复超时 25 秒，几十个残留套接字累加就是半分钟以上。
- **修复**：顺序改为「环境变量 → `~/.dbus/session-bus/` 记录（root 时扫 `/home/*/`）→ `/tmp` 扫描」，
  探测目标改成 `org.freedesktop.DBus.Peer.Ping`（只看 bus 是否活着），并加 `--reply-timeout=1000`。

### P2｜`find_panel()` 只认 `xfce4-panel`

- **根因**：Cinnamon / GNOME / MATE 上找不到面板 pid，只能退到 `SUDO_USER` 或 `$USER`；
  没有 sudo 时连 `XAUTHORITY` 都设不上。
- **修复**：按 `cinnamon` / `gnome-shell` / `xfce4-panel` / `mate-panel` / `plasmashell` /
  `budgie-panel` / `lxpanel` / `lxsession` / `marco` / `muffin` 顺序探测。

### P3｜`relaunch_as()` 让 root 父进程常驻

- **根因**：`su ... .status()` 阻塞等待托盘退出，`Exec=sudo networkmgr-rust` 启动后
  进程列表里永远多一个 root。
- **修复**：改用 `.spawn()`，失败打印错误；调用方随后 `exit(0)`，root 进程立即消失。

### 追加：普通用户运行时的提权路径（2026-11-09 用户实测反馈）

普通用户运行托盘时点「修复控制接口」直接报"没有权限"。

- **根因**：该动作在进程内直接 `read` / `write` `/etc/wpa_supplicant.conf`（`root:wheel 0600`），
  而托盘经 `relaunch_as()` 以普通用户身份运行；`sudoers.d/networkmgr-rust` 只放行了
  `networkmgr-rust` 整个二进制，没有 `apply-config`，所以既读不了也写不了。
- **修复**：
  1. 新增 `run_privileged()`：先 `sudo -n`（sudoers 免密条目，不打扰用户），
     再 `pkexec`（polkit 认证对话框，Cinnamon / GNOME / XFCE / KDE 都自带 agent），
     都不可用才提示可复制的命令。**不自己实现密码框**——口令不该经过本进程。
  2. `sudoers.d/networkmgr-rust` 增加
     `%wheel ALL=(ALL) NOPASSWD: /usr/local/bin/apply-config --fix-wpa-ctrl`
     （只放行这一个子命令，不给整个二进制免密）。
  3. 失败改用 `UiRequest::Notice` 回主线程弹窗——从桌面启动时 stderr 是看不到的，
     之前只 `eprintln!` 等于没提示。
- **仍是已知限制**：写 `rc.conf`、`ifconfig down`、`service netif restart` 等其它特权操作
  在普通用户模式下同样受限，尚未逐一接入提权通道；阶段 4 收尾时要么统一走
  `sudo -n` + 更细的 sudoers 条目，要么改成 polkit 规则。

### 验证状态

- **尚未重新打包验证**：需要一个新版本（或重跑 `release.yml`）才能确认干净系统上 `pkg add`

## 43. 0.2.1：托盘运行时目录属主修复（2026-11-10）

VM 换成 MATE 桌面后，zemin 以普通用户运行 `networkmgr-rust` 报
`Error: OsError(Os { code: 13, kind: PermissionDenied, message: "拒绝访问" })` 并退出。

### 根因

- tray-icon 会在 `$XDG_RUNTIME_DIR/tray-icon/` 下建缓存目录。
- `/var/run/xdg/zemin` 是 lightdm 为会话创建的运行时目录；**11-09 用 root 验收时**
  留下了 `tray-icon/`（`root:zemin`、0755），普通用户对它只有 `r-x`。
- 重启后 zemin 自动登录 MATE，从终端启动时写缓存 → `EACCES`。
- **错误码为什么误导**：tray-icon 用 `io::Error::last_os_error()`，拿到的是**上一次**操作
  残留的 errno；`truss` 里看不到对应的失败系统调用，只能看到进程 `_exit(1)`。
  这也是"重启后才坏"的原因——之前所有验收都是 root/daemon 跑的，自己写自己的目录。

### 修复

- 新增 `fix_tray_runtime_dir()`：启动时比对 `$XDG_RUNTIME_DIR/tray-icon` 的 uid，
  不是当前用户就删掉（目录里只有缓存，重建代价为零）。
- `TrayIconBuilder::build()` 的失败改用 `match`，打印可执行的排查提示
  （`rm -rf "$XDG_RUNTIME_DIR/tray-icon"`），不再只丢一个 `code: 13`。
- `is_root()` 改为复用新加的 `current_uid()`。

### 验证

- 复现：带 `XDG_RUNTIME_DIR` 启动 → EACCES；去掉即 `tray ready`。
- 修复后以 zemin + 真实会话环境启动 → `tray ready`，目录重建为 `zemin:zemin`。
- `cargo test --no-default-features --features sni`：GUI **12 passed**，`cargo fmt --check` 干净。

### 发布

- 版本 0.2.0 → 0.2.1；新增 `docs/RELEASE-0.2.1.md`；仍只发 amd64。
